# 导航模块首次切换性能优化设计

## 背景与根因

平台主导航使用 Next.js `Link`，目标页面又在 `src/components/v1/entry.tsx` 中通过 `next/dynamic` 加载功能模块。路由预取不会稳定地提前执行这层动态导入，因此用户首次进入模块时需要等待额外代码块。在 `next dev --webpack` 下，未访问路由还会叠加首次现场编译。

## 目标

- 应用可交互后，在浏览器空闲时预加载当前用户可见的主导航模块。
- 用户指针进入某个导航项时，立即提高该模块的预加载优先级。
- 保留现有代码分包，不把全部业务模块并入首屏。
- 不改变导航、权限和页面功能行为。

## 设计

### 可复用模块加载器

将每个功能模块的 `import()` 定义为稳定、可复用的加载器。`next/dynamic` 与预加载逻辑共用同一个加载器，使浏览器模块缓存能复用已发起或已完成的请求。

公开两个纯函数接口：

- `preloadBaselineModule(moduleId)`：预加载单个已知模块，未知模块安全忽略。
- `preloadBaselineModules(moduleIds)`：批量预加载并为单个失败提供容错，不影响导航交互。

### 预加载时机

`BaselineShell` 在客户端挂载后，根据已计算的 `allowedModules` 构建可预加载清单：

1. 优先预加载除当前模块以外的可见主导航模块。
2. 有 `requestIdleCallback` 时在空闲阶段执行，并设置超时上限；不支持时使用短延迟定时器。
3. 导航链接的 `pointerenter` 和键盘 `focus` 会立即预加载目标模块，不等待空闲任务。
4. 组件卸载时取消尚未执行的空闲回调或定时器。

权限筛选仍以 `visibleModules` 为准，不预加载当前用户不可见的功能。

## 错误处理

预加载是性能优化，不是进入页面的前置条件。预加载失败时不显示全局错误，用户点击后仍由现有 `dynamic` 加载流程重试并展示加载状态。

## 测试与验证

- 单元测试先证明当前实现无法通过模块 ID 触发预加载。
- 验证每个可支持模块都映射到正确加载器，重复调用共用同一个 Promise，未知 ID 不抛错。
- 验证导航预加载目标只包含可见、可动态加载的模块。
- 运行相关单测试、TypeScript 检查和 ESLint。
- 分别记录冷启动与预热后的导航切换结果。开发服务器的首次路由编译时间单独记录，不当作生产环境前端切换指标。

## 范围边界

本次不拆分大型页面组件，不重构全局状态订阅，不改变路由结构。如预加载后热切换仍有明显主线程阻塞，再单独设计组件拆分与状态选择器优化。
