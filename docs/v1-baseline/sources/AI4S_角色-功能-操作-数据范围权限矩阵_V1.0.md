# AI4S 角色—功能—操作—数据范围权限矩阵 V1.0

> 版本：V1.0  
> 用途：作为 AI4S 后续 PRD、信息架构、权限设计、原型设计和研发实现的权限基线。  
> 说明：本矩阵基于当前已确认的 Unified Research Agent、科研空间、项目空间管理、科研资产等产品方案整理。

---

## 一、权限模型总原则

AI4S 不建议仅采用传统 RBAC，而采用以下组合模型：

> **系统角色 × 项目成员关系 × 空间角色 × 资产权限**

整体权限判断逻辑：

```text
系统角色
科研人员 / 项目负责人 / 科研管理人员 / 平台管理员……
        ↓
所属科研项目 Project ID
        ↓
当前科研空间 Space
个人空间 / 项目空间 / 课题空间
        ↓
具体对象权限
会话 / 任务 / 资产 / 实验 / 设备……
```

最终某个用户能否执行某项操作，不只取决于“用户是什么角色”，还取决于：

- 是否属于当前科研项目；
- 是否属于当前科研空间；
- 在当前空间中承担什么角色；
- 对具体对象是否获得授权；
- 数据范围是否覆盖当前对象。

建议研发侧统一按照以下规则判断：

```text
是否允许访问
=
系统角色权限
∩
Project 成员资格
∩
Space 成员资格
∩
对象 ACL
```

## 二、角色基线

当前建议采用 7 类系统权限角色：

| 角色 | 核心职责 |
|---|---|
| **科研人员** | 开展科研任务，使用 Research Agent、知识、技能、模型、工具、实验和科研资产 |
| **分析化验人员** | 承担实验、分析化验、实验执行、实验数据和结果输出等工作 |
| **项目/课题负责人** | 负责项目/课题科研任务、团队协同、进展和科研成果 |
| **科研项目管理人员** | 负责 AI4S 项目空间、课题空间、成员和空间权限管理 |
| **科研管理人员** | 掌握科研项目运行、进展、风险及成果情况 |
| **科研决策人员** | 关注科研整体态势、重大项目、资源、人才和决策事项 |
| **平台管理员** | 管理 AI4S 平台、用户、权限、空间、系统配置和资源治理 |

### 2.1 角色叠加原则

角色不是互斥关系，可以叠加。

例如：

```text
课题负责人
=
科研人员
+
项目/课题负责人
```

```text
院级科研负责人
=
科研人员（如本人参与科研）
+
科研决策人员
```

用户最终可见功能和可执行操作，由多个角色权限合并后确定。

| 操作 | 科研人员 | 项目/课题负责人 | 科研管理 / 决策人员 |
|---|---|---|---|
| 新建会话 | ✓ | ✓ | 按科研角色授权 |

### 4.2 Research Agent 数据范围

Research Agent 默认只能访问：

> **当前用户 + 当前 Project ID + 当前 Space + 已授权共享资源**

AI 不得因为具备技术检索或调用能力而绕过现有数据和权限体系。

# 五、历史会话权限

核心原则：

> **空间共享 ≠ 会话默认共享。**

| 对象 | 默认访问规则 |
|---|---|
| 个人空间会话 | 仅本人可见 |
| 课题空间中的个人会话 | 默认仅创建人可见 |
| 项目空间中的个人会话 | 默认仅创建人可见 |
| 主动共享会话 | 指定成员 / 指定空间可访问 |
| 协同科研任务会话 | 参与任务的成员可访问 |

即使用户属于同一个课题空间，也不默认开放所有私人 Agent 对话。

需要团队沉淀和复用的内容，应进一步形成：

> **Research Artifact / 科研资产**


### 项目/课题负责人

默认可访问：

- 所负责项目 / 课题范围内的科研资产。

并可根据权限执行：

- 共享；
- 确认；
- 发布申请；
- 项目资产管理。

但不自动拥有平台级删除权限。

# 十、跨课题科研资产共享权限

同一个 Project ID 下，不同课题空间支持授权共享。

例如：

```text
课题空间 A
   ↓
数据集 A
   ↓
共享至课题空间 B
```

共享时建议配置：

- 目标空间；
- 共享对象；
- 有效期；
- 权限级别。

权限级别至少包括：

```text
只读
可引用
可复制
可协作
```

不建议只做简单的“共享 / 不共享”二元权限。

## 11.4 权限分配层级

建议权限层级统一为：

```text

   ↓
```

- **资产所有者 / 负责人**：管理具体资产共享和对象级 ACL。

# 十二、科研管理人员权限

科研管理人员的定位是：

> **看、分析、关注、管理科研运行，而不是管理平台和空间 ACL。**

默认数据范围：

> 授权组织 / 授权项目范围。

主要权限包括：

- 查看科研管理工作台；
- 查看项目总体情况；
- 查看科研进展；
- 查看项目风险；
- 查看科研成果；
- 执行必要的科研管理操作；
- 进入外部科研项目管理系统。

不默认拥有：

- 用户系统角色配置；
- 项目 / 空间 ACL 配置；
- 平台资源配置；
- 他人私人 Agent 会话访问权限。

> **数据范围广 ≠ 操作权限大。**

# 十四、平台管理员权限

平台管理员负责：

- 用户与系统角色；
- Project / Space；
- 权限规则；
- 科研资源接入；
- 系统集成；
- 平台运维；
- 科研资产治理；
- 资源上下架；
- 异常处理。

但需要明确：

> **系统管理权 ≠ 科研内容业务查看权。**

即使平台管理员拥有技术管理权限，也不代表产品默认允许其查看：

- 科研人员私人 Agent 会话；
- 未共享科研草稿；
- 无业务授权的私有科研内容。

# 十五、数据范围统一定义

后续权限矩阵、接口、PRD 和研发实现统一采用以下数据范围：

| 数据范围 | 定义 |
|---|---|
| **SELF** | 本人数据 |
| **SPACE** | 当前科研空间 |
| **TOPIC** | 当前课题范围 |
| **PROJECT** | 当前科研项目范围 |
| **AUTHORIZED** | 明确授权 / 共享范围 |
| **GLOBAL** | 平台全局 |

> TOPIC 在底层本质上属于一种 Space，但在业务权限和产品设计中单独保留，便于产品、业务和研发理解。

# 十六、原型中必须体现的权限交互

权限不能只存在后台矩阵中，后续原型必须体现以下关键交互：

1. 右上角统一空间切换器；
2. 无权限资源不展示或明确显示受限状态；
3. 科研资产共享弹窗；
4. 跨课题共享授权；
5. 空间成员管理；
6. 空间角色分配；
7. 共享范围选择；
8. 用户退出 / 被移出空间后的数据处理；
9. Research Agent 调用资源时受现有权限体系约束；
10. Agent 可适度显示当前使用的空间资源和授权来源。

其中第 9 点为硬约束：

> **Research Agent 不得成为绕过权限体系的“超级账号”。**

---

# 十七、权限体系最终结论

AI4S 权限体系可以统一概括为：

> **系统角色控制“能做什么”，Project / Space 控制“在哪做”，数据范围控制“能看到多少”，Asset ACL 控制“具体对象能不能用”。**

权限模型最终由以下四层共同决定：

```text
System Role
    ↓
Project Membership
    ↓
```
